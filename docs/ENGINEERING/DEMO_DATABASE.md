# The demo database

Cirqles runs against a local database that needs nothing installed. Clone the
repository, `npm install`, `npm run db:setup`, `npm run dev`.

This document explains what that database is, why it is not SQLite, and what is
not finished about it.

## Why not SQLite

SQLite was the obvious choice and it is the wrong one for this repository.

The schema is sixteen `pg-core` files. It uses `jsonb` columns with
`'[]'::jsonb` defaults, `onConflictDoNothing({ target })` with named conflict
targets, and - the one that matters - a `SELECT ... FOR UPDATE` row lock that
`registerForEvent` takes on the event row before reading `registered_count`.
That lock is why two students clicking register on the last seat at the same
moment cannot both get it.

SQLite has no `jsonb`, no `FOR UPDATE`, and different conflict syntax. Adopting
it would mean a second dialect of every schema file, a second set of
migrations, rewriting the 24 database tests, and giving up the concurrency
guarantee the waitlist rests on. That is a rewrite of the data layer to avoid an
install.

## What it is instead

[PGlite](https://pglite.dev) - Postgres itself, compiled to WebAssembly,
running in-process against a directory. Not a Postgres-like database: the same
query planner and the same SQL.

Which means:

- The migrations in `drizzle/` apply unchanged.
- `jsonb`, `FOR UPDATE` and `ON CONFLICT` all behave as they do in production.
- The database tests can run against it.
- Resetting is deleting a folder.
- Nothing to install, no Docker, no service to start.

The data lives in `data/cirqles-demo/`. It is a directory, not a file, because
it is a Postgres data directory.

## Switching databases

One function, `createDatabase` in `lib/db/driver.ts`. Every service imports `db`
from `lib/db` and none of them can tell which engine answered.

| Situation | Mode |
| --- | --- |
| No `DATABASE_URL` | demo |
| `DATABASE_URL` set | postgres |
| `CIRQLES_DB=demo` | demo, even with `DATABASE_URL` set |
| `CIRQLES_DB=postgres` | postgres, and errors if `DATABASE_URL` is missing |

Demo is the default deliberately. A fresh clone with no `.env.local` should
start, not crash on the first query.

Going to a hosted Postgres later is setting `DATABASE_URL` and running
`npm run db:migrate`. No application code changes, because none of it knows.

The demo driver is loaded through `createRequire` rather than a static import,
so the WASM build of Postgres is not bundled into deployments that will never
use it.

## Commands

| Command | What it does |
| --- | --- |
| `npm run db:setup` | Create the demo database if absent, migrate, seed. Safe to re-run. |
| `npm run db:reset` | Delete `data/cirqles-demo/`, then do the above. Destructive. |
| `npm run db:seed` | Seed only. Idempotent - every insert is `onConflictDoNothing`. |
| `npm run db:migrate` | Apply migrations to a real Postgres. Unchanged. |

`db:setup` is not destructive and `db:reset` is. That distinction is the whole
reason there are two commands: `db:reset` is the one to run five minutes before
a demo, and it should be obvious which one that is.

## Not finished

**The five new tables have no migration.** `saved_items`, `notifications`,
`posts`, `reports` and `opportunities` exist in `lib/db/schema/` but not in
`drizzle/`, so `db:setup` will not create them yet.

This is deliberate rather than an oversight. Migrations in this repository are
generated by `drizzle-kit`, never hand-written, and CI fails if
`drizzle-kit generate` produces a diff. Writing the SQL by hand would pass
locally and fail that check, and would break the guarantee that the schema
files and the migration history cannot disagree.

Run it once, locally:

```bash
npm run db:generate   # writes drizzle/00NN_*.sql
npm run db:reset      # rebuild with the new tables
```

Review the generated SQL before committing it, as with every other migration
here.

**Nothing in this document has been executed.** It was written without network
access, so `npm install`, `db:setup`, `db:generate` and the test suite have not
been run against it. Treat the commands as intended behaviour that needs
confirming, not as verified output.
