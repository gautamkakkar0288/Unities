# Engineering Decisions

Locked 2026-08-06. Changes require updating this file.

- **D1 — Canonical repo:** This repository is the product. The `gautamkakkar0288/Cirqles` pnpm monorepo (Express 5 + Drizzle + Orval) is superseded and should be archived.
- **D2 — Backend shape:** Next.js App Router monolith (route handlers + server actions). PostgreSQL via Drizzle lands in Phase 2. Redis introduced only when a measured need exists.
- **D3 — Auth:** Auth.js (next-auth v5) with database-backed user records via the Drizzle adapter. Satisfies server-side role claims per `docs/ENGINEERING/ARCHITECTURE.md`.
- **D4 — Client data:** TanStack Query (server state), React Hook Form + Zod (forms), Zustand (local state only).
- **D5 — Theming:** next-themes, light-first default, dark-ready tokens. Dark toggle ships when the theme system is formalized (Phase 3).
- **D6 — Phase ordering:** The 16-phase delivery order (Foundation → Auth → Design System → Landing → Core Layout → Communities → Posts → Events → Profiles → Search → Messaging → Notifications → Operations Center → AI → Performance → Production) supersedes `ROADMAP.md` numbering.
- **D7 — Package manager:** npm. Lockfile regenerated at the end of Milestone 1.
- **D8 — Session strategy (JWT first):** The Auth.js `Credentials` provider only supports the JWT session strategy, so Phase 2 ships JWT sessions. `ARCHITECTURE.md` asks for server-revocable sessions, which JWTs cannot provide instantly. The `sessions` table is created now, so adopting database sessions once OAuth / magic-link providers land is a configuration change rather than a migration. Mitigation until then: short token lifetimes and role claims re-read on sign-in.
- **D9 — Password hashing:** bcrypt (`bcryptjs`) at cost factor 12, executed server-side only. Passwords are capped at 72 characters in the Zod schema because bcrypt silently truncates beyond that length.
- **D10 — Edge/runtime split:** `auth.config.ts` contains no database or bcrypt imports so `middleware.ts` stays edge-compatible; the full configuration with the Drizzle adapter lives in `auth.ts` and runs only in the Node runtime.
- **D11 — Two-layer token architecture:** shadcn utility tokens (`background`, `card`, `muted`, `secondary`, `accent`, `border`) keep their neutral **surface** role, and Cirqles adds explicit **meaning** tokens (`primary`, `support`, `featured`, `success`, `warning`, `info`, `destructive`), each with `base` / `subtle` / `border` / `foreground` variants as required by `docs/DESIGN/02-Color-System.md`. Rejected alternative: remapping shadcn `secondary` to Soft Indigo and `accent` to Warm Orange. That reads cleaner in the docs but would repaint every neutral hover surface orange, because shadcn primitives use `accent` for hover states. Separating surface from meaning keeps primitives untouched and makes status colours explicit at call sites.
- **D12 — Theme state via next-themes, not Zustand:** `docs/DESIGN/10-Theme-System.md` specifies a global Zustand `store/theme`. That document predates the App Router decision. A client store cannot set the theme class before first paint, so it guarantees a flash of the wrong theme on every load. next-themes writes the class in a blocking pre-hydration script, which is the only correct approach for SSR. Zustand remains the choice for genuine client state (D4). `10-Theme-System.md` should be updated to reflect this.
- **D13 — Dark mode ships in Phase 3:** `10-Theme-System.md` and `DESIGN_SYSTEM.md` §4 treat dark mode as post-MVP. Retrofitting a theme after product surfaces exist is materially more expensive than tokenising once, and both documents already mandate full tokenisation up front. Dark mode therefore ships now as a designed palette (not an inversion, no pure black), with light remaining the default for new visitors.
- **D14 — Concrete token values are owned by `docs/DESIGN/13-Design-Tokens.md`:** that file asked for exact values to be appended once finalised. They now live there, mirroring `app/globals.css`. Any new colour, type size, radius, shadow, or duration must be added to the token set first and consumed via a utility class; components never hardcode raw values.
- **D15 — Route groups split public from authenticated:** the marketing site lives in `app/(marketing)/` with its own header and footer; the signed-in product shell lives in `app/(app)/`, and auth screens in `app/(auth)/`. Rejected alternative: one root layout that branches on session state. That forces every page through a conditional shell, couples marketing chrome to auth, and makes the marketing pages harder to keep fully static. Route groups give each audience its own layout with no runtime branching.
- **D16 — No fabricated social proof:** the landing page contains no invented user counts, testimonials, university logos, or "trusted by" metrics. Pre-launch, every such number would be a lie, and `docs/PRD.md` §3 makes trust a product feature rather than a marketing layer. Credibility is carried instead by honest positioning ("Now piloting at Chitkara University"), concrete problem statements, and verifiable product mechanics. Real metrics and testimonials get added once they exist.
- **D17 — Marketing copy as typed data:** all landing copy lives in `lib/marketing/content.ts`, not inline in JSX. Copy changes far more often than layout and is what a non-engineer will want to edit; typed data means such edits cannot break markup, the same strings feed both the page and its metadata and structured data, and adopting a CMS later replaces one module instead of rewriting components.
- **D18 — Desktop sidebar excludes Search and Notifications:** the two navigation documents disagree. `docs/UX/00-Information-Architecture.md` lists Home, Explore, Search, Notifications, Saved, Communities, Profile in the desktop sidebar; `docs/UX/02-Navigation-System.md` lists Home, Explore, Communities, Saved, Profile. Both agree the top bar owns global search and the notification indicator. Following the IA list would give Search and Notifications two competing entry points on the same screen, which is exactly the "where do I go now?" hesitation the navigation doc exists to prevent. We follow the navigation-specific document: sidebar for places, top bar for tools. Mobile keeps the mandated five-item bar unchanged. `00-Information-Architecture.md` should be updated to match.
- **D19 — The marketing page stays static for signed-in users:** visiting `/` while authenticated shows the marketing site rather than redirecting to `/home`. Redirecting would require reading the session on the landing page, making the most cacheable, highest-traffic page in the product dynamic in order to serve a rare case. Instead, sign-in lands directly on `/home`. A session-aware header on the marketing site can come later behind partial prerendering, where it costs nothing.
- **D20 — No user dropdown menu until a Menu primitive exists:** the sidebar shows a visible identity card with a sign-out button instead of an avatar dropdown. Phase 3 deliberately shipped no Menu primitive, and hand-rolling one requires correct roving focus, `aria-activedescendant`, type-ahead, and Escape handling to avoid being a keyboard trap. A visible card is more accessible than a bad menu, costs the user no extra click, and keeps the current role permanently visible, which supports the trust-first requirement. The dropdown arrives with the primitive.
- **D21 — A clickable prototype is built before the data layer (Phase 6-P):** the sixteen product screens are built at `/prototype/*` against fixture data before Phase 6 writes any schema. The reason is sequencing risk, not impatience: Phases 6 through 13 each end in a database migration, and discovering in Phase 8 that events need a waitlist state, or in Phase 11 that messaging needs a scope, means rewriting tables that already have code depending on them. Designing the vocabulary first — `lib/domain/types.ts` — and pressure-testing it against every screen makes the schema a transcription of a model that has already been reviewed. Rejected alternative: Figma mockups. They would answer the same design questions but produce nothing the product keeps, and they cannot prove the token system, spacing scale, or component APIs actually hold together in a browser.
- **D22 — The prototype is throwaway; the components it uses are not:** screens live in `app/(prototype)/`, a route group deleted wholesale in Phase 16 alongside `/design`. The components those screens render — `CommunityCard`, `EventCard`, `PostCard`, `CommentItem`, `VerificationBadge` — live in their real feature folders and graduate into Phases 6 to 9 untouched, because they take domain types as props and never reach for data themselves. All display and eligibility logic lives in `lib/domain/*` (`membership.ts`, `registration.ts`, `moderation.ts`, `messaging.ts`, `notifications.ts`, `search.ts`) with unit tests, so the rules survive even the deletion of every screen that currently demonstrates them. What is genuinely disposable is only the sixteen `page.tsx` files and `lib/prototype/`.
- **D23 — Prototype fixtures are deterministic and deliberately awkward:** `lib/prototype/fixtures.ts` pins a fixed `prototypeNow` instead of calling `new Date()`. A prototype whose relative timestamps differ between server render and client hydration produces mismatch warnings and cannot be screenshotted or reviewed twice, and every formatter in `lib/format.ts` therefore takes `now` as an explicit argument. The fixtures also include a full event, a pending join request, an unverified community, a closed registration, a broadcast-only channel, and a name long enough to wrap, because happy-path fixtures hide exactly the layout and copy failures a prototype exists to expose.
- **D24 — The prototype adds no new interactive primitives:** tabs, dialogs, sheets, and dropdowns are expressed as routes, links, and native `<details>` rather than hand-rolled components. Building a Dialog or Tabs primitive requires focus trapping, scroll locking, `aria-controls` wiring, and Escape handling to not be a keyboard trap, and the prototype's purpose is to validate layout and copy, not to ship half-finished accessibility. The one exception is the settings switch, which uses correct `role="switch"` and `aria-checked` markup with no state, so replacing it with a real primitive changes no screen's shape. Interest chips and filters are links for the same reason, with the side benefit that a filtered view becomes shareable.
